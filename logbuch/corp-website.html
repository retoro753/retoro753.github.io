> Überblick

„Corp Website“ ist ein Linux-Ziel mit einer Firmen-Webseite. Offen sind nur zwei Ports: SSH und ein Webserver. Die Webseite läuft auf einem veralteten Web-Framework mit einer kritischen Lücke. Darüber bekommt man ohne Login eine Shell und wird am Ende über eine lasche sudo-Regel zu root.

  • Web-App: Port 3000, Next.js 16.0.6
  • SSH: Port 22
  • Einfallstor: CVE-2025-55182 (unauthentifizierte RCE)
  • Privesc: sudo /usr/bin/python3 (NOPASSWD)

> Aufklärung

Zuerst alle Ports scannen, nicht nur die üblichen:

nmap -p- -T4 ZIEL-IP     # nur 22 (SSH) und 3000 (Web)

Beim Verzeichnis-Scan meldete dirb einen Treffer auf /cgi-bin. Der war aber gar nicht echt. So habe ich das geprüft:

curl -i http://ZIEL-IP:3000/cgi-bin/          # vermeintlicher Treffer
curl -i http://ZIEL-IP:3000/gibtesnichtxyz/   # bewusst erfundene Adresse

Beide gaben 404 zurück. Der „Treffer“ war also nur Rauschen des Scanners. Das nennt man einen Soft-404: Die Seite antwortet auf alles, statt bei Unsinn einen echten Fehler zu liefern. Merksatz: einen verdächtigen Fund immer gegen eine frei erfundene Adresse gegentesten.

Welche Software läuft? Ein Blick mit dem Browser-Plugin Wappalyzer zeigte Next.js 16.0.6. Die genaue Version ist Gold wert, denn damit findet man die passende Schwachstelle.

> Erster Zugang

Für Next.js 16.0.6 gibt es CVE-2025-55182: eine unsichere Deserialisierung in den React Server Components. Die Eckdaten:

  • Schweregrad CVSS 10.0, also das Maximum
  • unauthentifiziert, man braucht keinen Login
  • betroffen sind Next.js 16.0.0 bis 16.0.6, behoben in 16.0.7 — das Ziel läuft auf 16.0.6, passt also

Für solche frischen Framework-Lücken findet searchsploit meist nichts. Die funktionierenden PoCs (Proof of Concept, also ein Beispiel-Exploit) liegen auf GitHub. Damit ließ sich zuerst prüfen, ob das Ziel verwundbar ist, und dann eine Shell öffnen:

# 1. Prüfen, ob verwundbar
python3 CVE-2025-55182.py -u http://ZIEL-IP:3000           # Vulnerable: 1

# 2. Interaktive Shell öffnen
python3 CVE-2025-55182.py -u http://ZIEL-IP:3000 --exploit

Damit landet man als Web-Benutzer (hier webuser) auf dem System und kommt an die User-Flag.

Hinweis: Wo fange ich an?

Erst die genaue Version des Frameworks bestimmen (Wappalyzer oder HTTP-Header), dann gezielt nach „<Framework> <Version> CVE“ suchen. Nicht wild Exploits raten.

> Rechte ausweiten

Erster Reflex nach dem Zugang: Was darf dieser Benutzer als root tun?

sudo -l
    (root) NOPASSWD: /usr/bin/python3

Das heißt: webuser darf python3 als root starten, ohne Passwort. Python kann beliebige Befehle ausführen, also ist das praktisch ein Generalschlüssel. Solche „Wie werde ich damit root?“-Tricks stehen gesammelt bei GTFOBins.

Hinweis: Was tun mit sudo python3?

Schau bei GTFOBins unter „python → Sudo“. Python kann mit os.system oder os.listdir als root auf Dateien zugreifen, die dir sonst verwehrt sind.

> Sackgassen

Die Shell aus dem Exploit ist kein echtes Terminal. Sie zerbrach an einfachen Anführungszeichen ('...'): Jeder Befehl mit Anführungszeichen gab nur eine Statuszahl zurück, aber keine Ausgabe.

echo 'test123'      # nur eine Zahl, kaputt
python3 --version   # funktioniert

Also lag es an den Anführungszeichen, nicht an Python oder sudo. Mein Python-Einzeiler für die Privesc brauchte aber genau solche Anführungszeichen.

Lösung – der Umweg über Base64: Ich habe den Python-Code auf meiner Angriffs-VM (retoro_neo) als Base64 kodiert. Base64 besteht nur aus Buchstaben und Zahlen, enthält also keine Anführungszeichen. Auf dem Ziel wird er wieder dekodiert und direkt an sudo python3 weitergereicht:

# auf meiner Angriffs-VM (retoro_neo): Code zu Base64 machen
echo 'print(open("/root/root.txt").read())' | base64

# in der kaputten Shell: dekodieren und als root ausführen
echo <BASE64> | base64 -d | sudo /usr/bin/python3

So lässt sich die Root-Flag auslesen, ohne dass ein einziges Anführungszeichen durch die Shell muss.

> Gelernt

  • Scanner lügen manchmal: einen Treffer mit dem Soft-404-Test gegenprüfen.
  • Methodik: scannen → Software bestimmen → Version → passende CVE → Exploit → Privesc.
  • searchsploit kennt frische Framework- und npm-Lücken oft nicht. PoCs leben auf GitHub.
  • sudo -l ist beim Privesc immer der erste Check.
  • GTFOBins ist das Nachschlagewerk für „darf X als sudo – wie werde ich damit root?“.
  • Eingeschränkte Shells umgehen: Wenn Zeichen gefiltert werden, hilft Base64 als Transportweg.

No flags, no passwords. This is about the path, not about copying answers. The target IP changes per session and appears here as ZIEL-IP.

> Overview

"Corp Website" is a Linux target running a company website. Only two ports are open: SSH and a web server. The site runs on an outdated web framework with a critical flaw. That gives an unauthenticated shell, and a loose sudo rule then leads to root.

  • Web app: port 3000, Next.js 16.0.6
  • SSH: port 22
  • Entry point: CVE-2025-55182 (unauthenticated RCE)
  • Privesc: sudo /usr/bin/python3 (NOPASSWD)

> Recon

First scan all ports, not just the common ones:

nmap -p- -T4 ZIEL-IP     # only 22 (SSH) and 3000 (web)

During directory scanning, dirb reported a hit on /cgi-bin. But it wasn't real. Here's how I checked:

curl -i http://ZIEL-IP:3000/cgi-bin/          # supposed hit
curl -i http://ZIEL-IP:3000/doesnotexistxyz/  # deliberately made-up path

Both returned 404. So the "hit" was just scanner noise. This is called a soft 404: the site answers everything instead of returning a real error for nonsense. Rule of thumb: always test a suspicious finding against a made-up path.

What software is running? A quick look with the browser plugin Wappalyzer showed Next.js 16.0.6. The exact version is worth its weight in gold, because it leads you to the matching vulnerability.

> Initial access

For Next.js 16.0.6 there is CVE-2025-55182: insecure deserialization in React Server Components. The key facts:

  • CVSS severity 10.0, the maximum
  • unauthenticated, no login needed
  • affects Next.js 16.0.0 to 16.0.6, fixed in 16.0.7 — the target runs 16.0.6, so it fits

For fresh framework flaws like this, searchsploit usually finds nothing. The working PoCs (proof of concept, i.e. an example exploit) live on GitHub. With one I first checked whether the target was vulnerable, then opened a shell:

# 1. Check whether vulnerable
python3 CVE-2025-55182.py -u http://ZIEL-IP:3000           # Vulnerable: 1

# 2. Open an interactive shell
python3 CVE-2025-55182.py -u http://ZIEL-IP:3000 --exploit

This drops you onto the system as the web user (here webuser) and gives access to the user flag.

Hint: where do I start?

First determine the exact framework version (Wappalyzer or HTTP headers), then search specifically for "<framework> <version> CVE". Don't guess exploits at random.

> Privilege escalation

First reflex after getting in: what may this user do as root?

sudo -l
    (root) NOPASSWD: /usr/bin/python3

That means webuser may run python3 as root without a password. Python can run arbitrary commands, so this is effectively a master key. These "how do I get root with this?" tricks are collected at GTFOBins.

Hint: what to do with sudo python3?

Check GTFOBins under "python → Sudo". Python can use os.system or os.listdir to reach files as root that are otherwise off limits.

> Dead ends

The shell from the exploit isn't a real terminal. It broke on single quotes ('...'): every command with quotes returned only a status number, no output.

echo 'test123'      # only a number, broken
python3 --version   # works

So the quotes were the problem, not Python or sudo. But my Python one-liner for the privesc needed exactly those quotes.

Solution – the detour via Base64: I encoded the Python code as Base64 on my attack VM (retoro_neo). Base64 is only letters and numbers, so it contains no quotes. On the target it's decoded again and piped straight into sudo python3:

# on my attack VM (retoro_neo): turn the code into Base64
echo 'print(open("/root/root.txt").read())' | base64

# in the broken shell: decode and run as root
echo <BASE64> | base64 -d | sudo /usr/bin/python3

That reads the root flag without a single quote ever passing through the shell.

> Lessons learned

  • Scanners sometimes lie: verify a hit with the soft-404 test.
  • Method: scan → identify software → version → matching CVE → exploit → privesc.
  • searchsploit often doesn't know fresh framework and npm flaws. PoCs live on GitHub.
  • sudo -l is always the first check for privesc.
  • GTFOBins is the reference for "may run X as sudo – how do I become root?".
  • Getting past restricted shells: when characters are filtered, Base64 works as a transport.
